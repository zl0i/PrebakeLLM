# Понятия GPU и LLM для C++-разработчика

Коротко и только то, что нужно для понимания решений проекта. Раздел будет пополняться.

## Почему генерация упирается в память, а не в вычисления

При генерации каждый новый токен — это одно умножение «вектор × матрица» для каждой матрицы весов. Каждый байт весов читается из памяти один раз и участвует всего в паре операций (умножение и сложение). Процессору или GPU не хватает данных, а не вычислительной мощности. Поэтому:

> **токенов/с ≈ пропускная способность памяти ÷ байт весов, прочитанных на один токен**

Отсюда два способа ускориться: читать меньше байт (квантование, MoE) или читать из более быстрой памяти (VRAM 454 ГБ/с вместо RAM 76 ГБ/с).

Обработка промпта устроена иначе: сотни токенов умножаются на одну и ту же матрицу сразу. Там каждый байт весов переиспользуется много раз, и упираемся уже в вычисления.

## MoE (Mixture of Experts)

Вместо одного большого блока FFN в каждом слое лежит 256 маленьких «экспертов». Маленькая сеть-роутер для каждого токена выбирает 8 из них. Модель весит 35 млрд параметров, а на токен работает только около 3 млрд. Каких именно экспертов выберут, заранее неизвестно. Отсюда вся задача планирования: каких экспертов держать в быстрой VRAM.

## Ядро (kernel)

Функция, которую CPU отправляет на GPU и которая выполняется там в тысячах копий (потоков) одновременно. Каждая копия знает свой номер (`threadIdx`, `blockIdx`) и обрабатывает свой кусочек данных. «Запуск ядра» — асинхронная команда: CPU кладёт её в очередь и идёт дальше. На Windows (драйвер WDDM) постановка одного ядра стоит около 4.7 мкс времени CPU (замер в BENCHMARKS.md).

## Warp, блок, SM

- **Warp** — 32 потока, которые GPU исполняет строго синхронно, одной инструкцией (как SIMD-регистр шириной 32). Если потоки внутри warp пошли по разным веткам `if`, ветки выполняются по очереди.
- **Блок** — группа warp-ов (обычно 128–1024 потока). У блока есть общая быстрая память (shared memory), и его потоки могут синхронизироваться между собой.
- **SM** (streaming multiprocessor) — «ядро» GPU. У 4070 Super их 56, каждый одновременно выполняет несколько блоков.

## CUDA Graphs

Цепочку из сотен запусков ядер можно один раз «записать» и потом запускать одной командой. Это убирает накладные расходы CPU на каждый запуск. Важно, когда ядра маленькие, а при генерации одного токена они как раз маленькие.

## Pinned-память

Обычную память ОС может выгрузить в своп, поэтому GPU не может читать её напрямую: драйвер сначала копирует данные в промежуточный буфер. Закреплённую (pinned, page-locked) память GPU читает сам по PCIe, и это быстрее и асинхронно.

## Квантование

Веса хранятся не в 16 битах, а примерно в 4.5 (Q4_K_M): группами по 32–256 чисел, с общим масштабом на группу. Байт на токен становится в 3.5 раза меньше, за это платим небольшой потерей точности. В этом проекте квантование **не меняем**: сравниваемся на одном и том же файле.

## Спекулятивное декодирование (MTP, DFlash)

Маленькая быстрая «голова» угадывает несколько следующих токенов. Большая модель проверяет их одним проходом: проход по нескольким токенам стоит почти столько же, сколько по одному, потому что веса читаются один раз. Угаданные токены принимаются, на первом неугаданном цепочка обрывается. При жадной генерации результат **точно такой же**, как без спекуляции, просто быстрее. У MoE есть подвох: разные токены выбирают разных экспертов, поэтому проверка нескольких токенов читает больше весов.

## Почему промах кэша выгоднее считать на CPU, чем везти на GPU

Эксперт весит ~1.8 МБ. Чтобы GPU его посчитал, эти байты надо прочитать один раз:
- **GPU читает их из RAM по шине PCIe:** ~22 ГБ/с, то есть ~80–90 мкс.
- **CPU читает их из той же RAM:** ~76 ГБ/с на 8 ядрах, то есть ~25–35 мкс с учётом счёта.

Работы у CPU при генерации немного, а память у него своя. Поэтому выгодно делить работу: GPU считает экспертов, которые уже в VRAM, а CPU в это же время считает остальных. В сумме используются обе памяти сразу: 454 ГБ/с у VRAM и 76 ГБ/с у RAM.

## «Почта» между GPU и CPU

Обычный способ «спросить CPU» из середины вычислений GPU — остановить поток CUDA (`cudaStreamSynchronize`), прочитать данные и запустить продолжение. На Windows такой круг стоит десятки микросекунд, а в llama.cpp он повторялся 40 раз за токен.

Мы делаем иначе:
- Закреплённую (pinned) память видят и CPU, и GPU. GPU-ядро пишет туда номер запроса.
- Потоки CPU постоянно смотрят на эту ячейку (spin-wait), считают и пишут номер готовности.
- Маленькое ядро GPU ждёт этот номер и продолжает.

CPU при этом не вызывает ни одной функции CUDA, поэтому весь токен записывается в один CUDA-граф. Круг занимает ~4 мкс (`tools/pingpong`).

## Почему кэшу важна недавность, а не частота

Модель выбирает 8 экспертов из 256 в каждом слое. Соседние токены почти всегда выбирают почти тех же экспертов, и тема текста определяет набор «на ближайшее время». Поэтому:
- набор экспертов, заранее выбранный по общей частоте, попадает в 64–76% случаев;
- кэш, который держит недавно использованных, попадает в 85–90%.

Это видно в симуляции `tools/cachesim.py` по трассам `tools/trace_experts`.
