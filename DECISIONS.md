## D1. Модель для первой вехи: Qwen3.6-35B-A3B, файл unsloth UD-Q4_K_M (22.1 ГБ)

**Решение.** Qwen3.6-35B-A3B (Apache 2.0, апрель 2026). Конкретный файл — `unsloth/Qwen3.6-35B-A3B-GGUF` / `UD-Q4_K_M`.

**Почему эта модель.**
- Целиком в 12 ГБ не помещается: экспертов около 19 ГБ, а свободно примерно 10 ГБ VRAM. Значит, всё решает размещение весов между VRAM и RAM, а именно здесь у планировщика больше всего простора.
- На токен работают всего ~3 млрд параметров (8 из 256 экспертов на слой). Генерация остаётся быстрой даже тогда, когда часть весов лежит в RAM.
- Это популярная модель для такого железа, поэтому для неё есть сильные эталоны: llama.cpp и Strata с опубликованными цифрами. Победа над ними будет убедительной.
- У модели есть готовые «помощники» для спекулятивного декодирования, MTP и DFlash. Без них сравнение с лучшим llama.cpp было бы нечестным (см. D3).

**Особенности архитектуры, которые надо учитывать.**
- 40 слоёв. В 30 из них линейное внимание Gated DeltaNet: его состояние фиксированного размера и не растёт с длиной контекста. Обычное внимание стоит только в 10 слоях, и у него 2 KV-головы. Поэтому KV-кэш крошечный, около 20 КБ на токен (32К контекста — это ~650 МБ), и длинный контекст для этой модели дешёвый.
- В каждом слое 256 экспертов по 512 нейронов, на токен выбирается 8, плюс есть один общий (shared) эксперт.
- Словарь — 248 тыс. токенов. Головы `embed` и `lm_head` весят около 0.5 млрд параметров каждая.

**Рассмотренные альтернативы.**
| Модель | Почему не она |
|---|---|
| Qwen3-30B-A3B-2507 (18.6 ГБ) | Старше. Помещается почти наполовину, так что простор для планирования меньше |
| GLM-4.7-Flash 30B-A3B (18.3 ГБ) | Вариант хороший, но эталонов и готовых драфт-моделей меньше |
| Nemotron-3-Nano-30B-A3B (24.6 ГБ) | Гибрид с Mamba, поддержка в llama.cpp менее зрелая |
| gpt-oss-20b (12.1 ГБ) | Почти помещается целиком, так что планировать нечего |

**Квантование.** UD-Q4_K_M, как в ТЗ (Q4_K_M). MXFP4 и IQ4 отклонены, чтобы не путать сравнение: эталон и наш движок обязаны использовать один и тот же файл.

## D2. Эталон: официальная сборка llama.cpp b12189 (CUDA 13.5), исходники того же коммита 80d2c0c2c

Бинарники лежат в `third_party/llama-bin`, исходники в `third_party/llama.cpp`. Сборка официальная, потому что именно её реально скачивают пользователи, и её никто не сможет обвинить в «плохой сборке эталона». Когда поставим CUDA 13.x, соберём llama.cpp из исходников тем же компилятором, что и наш движок, и сверимся с официальной сборкой.

## D3. Что значит «llama.cpp с лучшими настройками»: эталон сильнее, чем кажется

Обзор (см. `docs/survey.md`) и проверка исходников показали, что в текущем llama.cpp уже есть:
- `--fit` (включён по умолчанию): автоматически подбирает, что положить в VRAM;
- `--n-cpu-moe N`: эксперты первых N слоёв лежат в RAM;
- `--moe-cache-mib N`: LRU-кэш экспертов в VRAM; эксперты, которых нет в кэше, подвозятся по PCIe;
- спекулятивное декодирование `--spec-type draft-mtp|draft-dflash|...` с готовыми драфтами для нашей модели.

**Решение.** Эталон — лучший результат перебора по этим параметрам: `-ncmoe`, `--moe-cache-mib`, `-t`, `-ub`, `-fa`, привязка к P-ядрам, MTP/DFlash и длина драфта. Перебор делаем скриптом, и сам скрипт входит в репозиторий.

**Честное предупреждение.** Strata (MIT) уже заявляет +15–20% к llama.cpp на этой модели (RTX 3060). Место занятое, и лёгкой победы не будет.

## D4. Основная гипотеза ускорения (проверяется на данных, план может поменяться)

По потолкам железа (BENCHMARKS.md):
1. Эксперты, которых нет в VRAM, **считать на CPU прямо в RAM, а не возить по PCIe**: CPU читает RAM в 3 раза быстрее, чем работает шина.
2. **CPU и GPU должны работать одновременно внутри слоя.** GPU считает своих («горячих») экспертов, CPU в это время считает «холодных». Сейчас llama.cpp выполняет части графа на разных устройствах по очереди.
3. **Какие эксперты класть в VRAM, решать по статистике использования**, собранной на этой машине. Сейчас llama.cpp раскладывает целыми слоями (`-ncmoe`) или кэширует по LRU.
4. **Сократить накладные расходы**: CUDA Graphs и меньше синхронизаций CPU↔GPU. Запуск ядра на WDDM стоит 4.7 мкс.
5. **Подобрать под машину** число потоков, привязку к ядрам, длину драфта и размер горячего набора. Это и есть та «сборка», которую сохраняем в кэш.

Основа — форк llama.cpp/ggml (MIT): загрузчик GGUF, квантованные ядра и CPU-бэкенд уже готовы и оптимизированы. Сначала измеряем, где реально уходит время у эталона, и только потом пишем код.

## D4a. Пересмотр D4 по данным (2026-11-07)

**Что не подтвердилось.** «Подвозить экспертов по PCIe невыгодно, считать промахи на CPU» — в такой форме неверно. LRU-кэш llama.cpp попадает в ~93% случаев: соседние токены используют почти одних и тех же экспертов. Промахов около 21 на токен, подвоз занимает 1.8 мс. Режим кэша (78 ток/с) обгоняет раскладку по слоям с CPU-экспертами (60 ток/с). Запись оставляю как неудачную гипотезу.

**Что показал профиль.** 37% времени токена GPU простаивает. Причина — 40 поездок на токен «GPU → CPU → GPU», в каждом слое по одной: так кэш узнаёт, кого подвезти. Сами ядра почти упираются в память.

**Новое направление, кандидат для вехи: «токен без участия CPU».**
1. В VRAM лежат горячие эксперты. Таблица «эксперт → адрес» хранится в памяти GPU: адрес указывает либо на слот в VRAM, либо прямо в pinned RAM.
2. Ядро MoE берёт адрес из таблицы. Промахи читаются из RAM напрямую, zero-copy, со скоростью 23 ГБ/с (замер). Синхронизаций с CPU внутри токена нет, и весь токен (вместе с проверкой MTP-драфта) можно записать одним CUDA-графом.
3. Какие эксперты держать в VRAM, CPU решает в фоне по номерам экспертов прошлых токенов (копируются асинхронно) и подменяет слоты между токенами. Решение отстаёт на 1 токен, но это не останавливает GPU.

Оценка: ~6.3 мс на чтение весов, плюс ~1–2 мс на промахи (частично параллельно), плюс мелочь. Получается 8.5–9.5 мс на токен против 12.8, то есть +35–50% без MTP. С MTP прирост, вероятно, ниже, потому что проверка драфта трогает больше экспертов.

**Риски и что проверить до написания ядра.**
- Хватит ли кэша с отставанием в 1 токен, и насколько он хуже LRU llama.cpp. Это проверяется дёшево: снимаем трассы выбора экспертов на разных промптах и моделируем кэш офлайн.
- Ядро MoE с таблицей адресов придётся написать самим, на основе `mul_mat_vec_q` из ggml (MIT).

**Альтернатива: промахи на CPU.** CPU свободен, но тогда каждому слою нужна поездка GPU→CPU→GPU. Это ровно та задержка, от которой мы хотим уйти. Отложено.

## D6. Движок: форк llama.cpp + «гибридные эксперты» (moe-zc), 2026-11-07

**Что сделано.** Форк llama.cpp от коммита эталона: `third_party/llama-fork`, ветка `engine`, патчи — в `engine/patches/`. Изменения минимальные и изолированные:
- `ggml/src/ggml-cuda/moe-zc.cu` — новый файл, вся логика;
- `mmvq.cu`, `mmq.cu` — несколько строк-хуков;
- `src/llama-moe-zc.cpp` — подключение к модели.

Без переменной `LLAMA_MOE_ZC_MIB` движок ведёт себя как обычный llama.cpp.

**Как работает генерация (шаг ≤ 4 токенов).**
1. Все эксперты лежат в закреплённой RAM. Часто используемые копируются в слоты VRAM (кэш). Для каждого тензора экспертов в памяти GPU есть таблица адресов: `table[e]` = адрес копии в VRAM или `nullptr`.
2. Ядро `mul_mat_vec_q` считает экспертов из таблицы и пропускает экспертов с `nullptr`.
3. Одновременно 8 потоков CPU, по одному на P-ядро, считают пропущенных экспертов прямо из RAM. Используются AVX2-ядра ggml-cpu: CPU читает RAM на ~76 ГБ/с, а по шине вышло бы ~22 ГБ/с.
4. Связь GPU↔CPU идёт через «почтовые ящики» в закреплённой памяти. Маленькое ядро GPU ставит флаг запроса, потоки CPU крутятся на флаге, считают и ставят флаг готовности; другое маленькое ядро GPU ждёт его и вписывает результаты на места пропущенных экспертов. Дальше граф llama.cpp идёт без изменений. CPU не вызывает CUDA API, так что весь токен остаётся одним CUDA-графом. Задержка такого «пинг-понга» — ~4 мкс (`tools/pingpong`).
5. После шага CPU обновляет кэш. Политика вытеснения — CRF из llama.cpp (MIT), то есть учитываются и давность, и частота использования. Подвоз идёт фоном одним пакетным вызовом `cudaMemcpyBatchAsync` и только после запуска графа следующего токена. Таблица публикуется синхронно между шагами, поэтому GPU и CPU всегда одинаково видят, какой эксперт где считается.

**Как работает обработка промпта (шаг > 4 токенов).** Тензор экспертов копируется во временный буфер VRAM, и дальше работает обычный `mmq`:
- ≤64 токенов — ядро-«сборщик» копирует только использованных экспертов (из слота VRAM или из RAM);
- больше — пакетный DMA: эксперты из кэша копируются VRAM→VRAM, остальные RAM→VRAM.

**Заимствования.** llama.cpp/ggml (MIT): весь движок, квантованные ядра CPU и GPU, политика CRF. Идея считать промахи на CPU параллельно с GPU известна по Fiddler (arXiv 2402.07033) и Strata (MIT, Niko1221). Их код не использовался: наша реализация с «почтой» без вызовов API и с таблицами адресов в CUDA-графе написана с нуля.

### Неудачные эксперименты на пути к D6

| # | Что пробовали | Результат | Почему не взяли |
|---|---|---|---|
| 1 | Статический «горячий набор» экспертов по частоте на калибровке | 64–76% попаданий в симуляции против 85–91% у LRU | Решает не частота, а то, что использовалось недавно |
| 2 | VMM: страницы VRAM и RAM в одном диапазоне адресов, «переезд» эксперта = переотображение | Работает на Windows (`tools/vmmtest`), 89 мкс на переотображение | Переотображение не атомарно: GPU может прочитать страницу посреди смены → крах. Безопасного окна без синхронизации нет |
| 3 | v1 «zero-copy»: GPU сам читает промахи из RAM по шине | Простой GPU упал с 37% до 8%, но 53–57 ток/с против 78 у llama.cpp | Каждый промах (~92 мкс по шине) стоит на критическом пути, а подвоз в кэш ещё раз гонит те же данные |
| 4 | v1 + LRU с правилом допуска «2 промаха за N токенов» | Трафик по шине упал лишь до ~105 МиБ/токен, доля попаданий снизилась | Не решает главную проблему из п. 3 |
| 5 | Подвоз отдельным потоком через ~90 мелких `cudaMemcpyAsync` | Запуск графа следующего токена ждал на блокировке драйвера, подвоз переставал идти параллельно | Исправлено пакетным вызовом и стартом подвоза после запуска графа: 74 → 81.5 ток/с |
| 6 | Собственный пул llama.cpp `-t 8` вместе с нашими 8 потоками | Под нагрузкой (профилировщик) потоки вытесняются, барьеры ждут квант планировщика: 340 мс на токен | `-t 1`: на генерации этому пулу всё равно нечего делать |
| 7 | Копирование номеров экспертов в графе (`ggml_cpy`) | Ломало слияние top-k у CUDA-бэкенда (+0.2 мс/токен) | Номера экспертов берутся из «почты» |

### Известные недостатки
- Обработка промпта медленнее llama.cpp на 15–30% (79/126/582 против 111/150/671 ток/с на 30/64/17К токенах). Причина — копирование экспертов в VRAM перед `mmq` не перекрывается с вычислениями.
- Доля попаданий в кэш ниже, чем у llama.cpp на том же объёме (85% против 89%). Новые эксперты становятся видны через 2 токена, слот на 7% больше эксперта (1.95 против 1.81 МиБ), остальная разница не объяснена.
- Поддерживаются только раздельные тензоры gate/up/down. Сдвоенный gate_up и раскладка llama.cpp `-ot` — не тестировались.

## D5. Окружение

- В VRAM рабочий стол занимает 1.2–2.5 ГБ. Это учитывается при планировании: «сборка» смотрит, сколько VRAM свободно на самом деле.
- CUDA Toolkit 11.8 устарел. 2026-11-07 владелец поставил рядом **CUDA 13.5** (`C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.5`, nvcc 13.5.37). Это та же версия, что у официальной сборки llama.cpp. С MSVC 17.8 собирается и работает: hwbench на 13.5 даёт те же цифры. Весь наш код дальше собираем на 13.5, путь к toolkit указываем в скриптах сборки явно и не полагаемся на `CUDA_PATH`.

**Откуда выигрыш.** В llama.cpp каждый промах кэша экспертов подвозится по шине на критическом пути, плюс в каждом слое GPU ждёт CPU. У нас промахи считает CPU параллельно с GPU, без остановок. Разница особенно заметна с MTP: проверка 3 токенов затрагивает больше разных экспертов.

**Чем заплатили:**
- обработка длинного промпта медленнее на 11% (605 против 677 ток/с);
- 6–8 ядер CPU заняты, пока идёт генерация.

**Что дальше (по ожидаемому эффекту):**
1. *Обработка промпта.* Подгружать экспертов следующего слоя, пока считается текущий (перекрыть копирование и счёт). Дать сборке выбирать `-ub`.
2. *Доля попаданий в кэш* (85% против 89% у llama.cpp на том же объёме). Свои пулы слотов для каждого размера эксперта. Меньше запаздывание публикации: снимок таблицы для каждого слоя вместо снимка на весь шаг.
3. *Скорость CPU-части.* 33–39 мкс на эксперта против ~24 мкс теоретических: программная предвыборка, деление работы между потоками без барьеров.
4. *Надёжность сборки.* Короткие пробы шумят на ±10%: повторять финалистов, следить за свободной VRAM во время работы.
5. *Обобщение* (после вехи, по ТЗ): другие MoE-модели (сдвоенный gate_up), другие GPU, облачный кэш сборок.

## D8. После вехи 1: проверки по разбору и вторая модель (2026-11-08)

**Что сделано:**
- **Честность эталона.** llama.cpp, собранный нашим тулчейном, идёт вровень с официальной сборкой (±1%), компилятор выигрыш не объясняет.
- **ik_llama.cpp.** Перебрано 15 конфигураций, лучшая — ~83 ток/с против ~105 у llama.cpp и ~124 у нас на Qwen3.6. На GLM ik не смог загрузить файл с MTP-слоем meshllm.
- **ktransformers.** Сравнение невозможно без смены ОС и формата весов: только Linux, только safetensors. Решение за владельцем.
- **Вторая модель — GLM-4.7-Flash** (deepseek2/MLA, 64 эксперта по 5.7 МБ, на токен 4, встроенный MTP-слой). Движок заработал без изменений кода: путь prefill побитово равен llama.cpp, путь генерации согласован с независимым эталоном «всё на CPU». Нашлась аномалия самого llama.cpp на одном куске wikitext (BENCHMARKS).
- **`aic build` стал устойчивее и шире:**
  - пробует драфт 0–3;
  - меряет расход VRAM отдельно с драфтом и без;
  - каждая проба — два прохода с медианой, два финалиста перемериваются;
  - две сборки подряд выбрали одно и то же.
- **«Компиляция под железо/модель» подтверждена.** Для Qwen3.6 сборка выбирает MTP 2 и кэш ~6.7 ГБ, для GLM — без спекуляции и кэш ~7.8 ГБ. Пересадка выбора одной модели на другую лишает движок преимущества (BENCHMARKS, «Пересадка настроек»).
- **Обработка промпта** (D7, п. 1) исправлена профилированием: копируем только использованных экспертов, теперь мы на 22–31% быстрее llama.cpp вместо −11%.
- **Простаивающие CPU-потоки засыпают** (патч 0005). Сервер без запросов CPU не грузит, во время генерации заняты ~7 логических CPU.

**Неудачное/отброшенное:**
- *Гипотеза «мешают мелкие DMA-копии» при prefill* опровергнута замером с `MIB=0`: дело было в объёме, а не в числе копий.
- *Гипотеза «llama.cpp на GLM тормозит из-за MTP-слоя на CPU»* опровергнута: с MTP-слоем на GPU llama.cpp не ускорился.

**Что дальше (по ожидаемому эффекту):**
1. Доля попаданий в кэш (85% против 89% у llama.cpp): отдельные пулы слотов по размеру эксперта, меньшее запаздывание публикации.
2. Скорость CPU-части: 33–39 мкс на эксперта против ~24 теоретических.
3. Третья модель или квантование другого размера, где модель почти помещается в VRAM: сборка должна выбрать почти чистый GPU-режим.
4. Энергопотребление CPU: на Windows нужен драйвер для счётчиков RAPL, иначе только доля занятых ядер.
